## Project Overview

A tool that takes a plain-English infrastructure requirement (e.g. "I need a web app
with a load balancer, 2 EC2 instances, and an S3 bucket for static assets") and:

1. Extracts a structured JSON representation of the required cloud resources via an LLM.
2. Converts that JSON into valid Terraform (HCL) using hand-written templates.
3. Validates the generated code with the real Terraform CLI (`terraform validate` /
   `terraform fmt`) — **never `terraform apply`**.
4. Displays the code (syntax-highlighted) and a basic resource diagram to the user.

This is a portfolio project. Priorities, in order: (1) everything that exists actually
works and is explainable, (2) scope stays narrow, (3) polish.

## Tech Stack

- **Backend:** Java 21, Spring Boot 3.x, Maven
- **LLM:** Google Gemini API (NL → structured JSON extraction only, never raw HCL)
- **Templating:** Plain Java string-based templates per resource type (no templating
  framework for v1 — keep it simple and debuggable)
- **Validation:** Terraform CLI, invoked via `ProcessBuilder` from the backend
- **Frontend:** React (Vite) + Tailwind CSS, Monaco Editor (code display), React Flow
  (resource diagram)
- **Database:** PostgreSQL, via Spring Data JPA — stores each generation request (input
  text, resulting JSON, generated HCL, validation status, timestamp) for a simple
  history view. Not used for auth or multi-tenancy in v1.
- **Containerization:** Docker Compose (backend + frontend + PostgreSQL as separate services)
- **CI:** GitHub Actions (lint + build on push, at minimum)

## Supported Resource Types (v1 scope — do not expand without discussion)

`vpc`, `subnet`, `internet_gateway`, `route_table`, `security_group`, `ec2`, `s3`

Adding a new type means updating **three places together**: the JSON schema, the
few-shot prompt examples, and the template engine. Don't add one without the others.

## Key Design Decisions

- **LLM never writes raw Terraform.** It only extracts structured JSON, constrained by
  a strict prompt + few-shot examples + schema validation on the response. HCL is
  always generated by our own hand-written templates. This is what guarantees
  syntactic correctness regardless of model reliability — don't bypass it.
- **Cloud provider is a pluggable abstraction, not a hardcoded assumption.** The
  template engine is built behind a `CloudTemplateProvider` interface. v1 ships only
  `AwsTemplateProvider`, but the JSON schema, controller, and prompt layer never
  assume "aws" — adding Azure/GCP later should mean writing a new implementation,
  not rewriting the system. Don't leak AWS-specific naming outside the `aws/` package.
- **Every generation request is persisted** (input text, generated JSON, generated
  HCL, validation status, timestamp) via `GenerationHistoryRepository`. This is
  intentionally minimal — no auth, no per-user scoping in v1, just a flat history log.
- **Resources reference each other via `_ref` fields** (e.g. `subnet_ref`, `vpc_ref`) in
  the JSON. These IDs are used both to wire up Terraform resource references and to
  build the React Flow diagram edges — one data model powers both.
- **[ASSUMPTION — confirm or override]:** Terraform CLI is installed directly in the
  backend's Docker image for v1 simplicity. Each validation request writes generated
  `.tf` files to an isolated temp directory, runs `terraform validate`, then deletes
  the directory. If stronger isolation is wanted later, this can move to a separate
  sandboxed worker service the backend calls out to.
- **Never call `terraform apply`, ever, anywhere in this codebase.** Validate/fmt only.

## Coding Conventions

- **Backend:** standard layered architecture (controller → service → model). Use DTOs
  for request/response; don't leak internal JSON-schema classes if they diverge from
  the API contract.
- **Frontend:** functional components + hooks only. Tailwind utility classes for
  styling — no CSS-in-JS, no separate stylesheets unless unavoidable.
- **Templates:** one file per resource type, named consistently
  (`vpc.tf.template`, `ec2.tf.template`, etc.) under `src/main/resources/templates/`.

## Environment Variables

- `GEMINI_API_KEY` — required
- `DB_URL`, `DB_USERNAME`, `DB_PASSWORD` — PostgreSQL connection (defaults provided in
  `docker-compose.yml` for local dev)
- AWS credentials are only needed later for actual deployment of this tool itself, not
  for `terraform validate`, which needs no cloud credentials.

## Common Commands

```
cd backend && mvn spring-boot:run      # run backend locally
cd frontend && npm run dev             # run frontend locally
docker-compose up --build              # run full stack
mvn test                               # backend tests
npm test                               # frontend tests (if configured)
```

## Testing Priorities

- **Highest value:** unit tests for the JSON → HCL template mapping logic. This is the
  most fragile part of the system and the easiest to silently break.
- Mock Gemini API responses in tests — don't hit the real API in the test suite.

## Explicitly Out of Scope for v1

- Multi-cloud support (Azure, GCP) — architecture is pluggable for this (see
  `CloudTemplateProvider`), but only `AwsTemplateProvider` ships in v1
- Cost estimation suggestions (stretch goal, not required for a working demo)
- Authentication / multi-user support (history table is flat, unscoped to a user)
- Editing generated Terraform code in the UI

## Guardrails

- Never let generated code path reach `terraform apply`.
- Never pass raw user input directly into a shell command — everything must go
  through the structured JSON → template pipeline first.
- If unsure about a resource type, dependency, or prompt behavior, ask rather than
  guessing — this file should stay accurate as decisions get made.
